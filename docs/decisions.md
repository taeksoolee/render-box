## D-01. 사용자: 기획자가 올리고 개발자·디자이너가 본다

- **맥락:** 처음에는 개발자가 HTML을 테스트하는 도구로 설계했다. 그런데 실제 수요는 기획자가 AI로 만든 HTML을 개발자·디자이너에게 공유하는 흐름이었다.
- **결과:**
  - 업로드 화면은 코드 편집이 아니라 파일 드래그와 붙여넣기 중심으로 만든다.
  - 기술 용어가 들어간 선택지(렌더링 프로필 등)를 없앴다.
  - AI 생성 HTML의 흔한 패턴(Tailwind CDN, `localStorage`, 상대 경로 이미지)에 대응한다.

## D-02. 인증: 개인별 접근 키

| 대안 | 기각 이유 |
| --- | --- |
| ID/비밀번호 | 외워야 하고, 비밀번호 해시·변경 화면·계정 잠금 등 부수 기능이 많다 |
| 팀 공용 키 하나 | 한 명이 퇴사하거나 키가 유출되면 전원이 키를 바꿔야 한다. 누가 올렸는지 추적할 수 없다 |
| Google Workspace 로그인 | 회사가 Workspace를 쓰지만, Google Cloud 쪽 OAuth 클라이언트 설정과 관리 부담이 생긴다 |
| 키를 URL에 포함 (`?key=`) | 브라우저 기록, 서버 로그, Referer로 키가 새어 나간다 |

- **결과:** 키는 약 190bit 난수로 만들고, DB에는 SHA-256 해시만 저장한다. 사람 단위로 회수할 수 있고, 역할 변경은 즉시 반영된다.
- **트레이드오프:** 운영자가 CLI로 키를 발급하고 전달해야 한다. 사용자가 수십 명을 넘으면 웹 관리 화면이나 SSO를 다시 검토한다.

## D-03. 렌더링: 새 창, iframe 미사용

| 대안 | 기각 이유 |
| --- | --- |
| 관리 화면 안의 iframe | 관리 화면에서 렌더링 호스트는 서드파티이므로, 서드파티 쿠키 차단(Safari, Firefox) 때문에 세션 쿠키가 안정적으로 전송되지 않는다. 별도 토큰이 필요해진다. 렌더링 문서의 무한 루프가 관리 화면까지 멈출 수 있다. iframe 크기와 sandbox 속성 때문에 실제 페이지와 결과가 달라진다 |

- **결과:** 렌더링은 항상 최상위 문서로 연다. 격리는 iframe 속성이 아니라 응답 헤더 CSP `sandbox`로 적용한다. 이 방식은 직접 접근할 때도 동일하게 적용된다.

## D-04. 관리·렌더링 호스트 분리

| 대안 | 기각 이유 |
| --- | --- |
| **단일 도메인** (`/r/*` 경로 + CSP sandbox) | 한때 채택했다가 독립 리뷰에서 뒤집었다. 이유는 아래 세 가지다 |
| 완전히 다른 등록 도메인 | 미리보기 POST가 cross-site가 되어 Lax 쿠키가 전송되지 않으므로 서명 토큰이 추가로 필요하다. 인증서와 DNS 관리 부담도 있다. 비로그인 공개를 도입할 때 다시 검토한다 |

단일 도메인을 기각한 이유:

1. **격리 전제가 틀렸다.** 설계는 "opaque origin 문서의 하위 요청에는 `SameSite=Lax` 쿠키가 실리지 않는다"고 가정했다. 그러나 RFC 6265bis는 sandbox가 걸린 최상위 문서의 site-for-cookies를 문서 URL의 출처로 계산한다. 따라서 같은 호스트로 보내는 `<img>`나 `fetch(credentials:'include')`에는 쿠키가 실린다. 이 전제를 검증하던 테스트는 `fetch`의 기본 credentials 설정 때문에 전제가 틀려도 항상 통과하도록 짜여 있었다.
2. **실패하면 전부 열린다(fail-open).** CSP 헤더가 한 번이라도 빠지면 사용자 JS가 관리 화면과 같은 출처가 되어 계정 전체가 탈취된다. 프록시가 헤더를 덮어쓰는 등 앱 밖에서 생기는 누락은 CI로 잡을 수 없다.
3. **신뢰하는 주소에서 피싱이 가능하다.** 렌더링 문서가 관리 화면과 같은 주소창 아래에서 가짜 입력 화면을 띄울 수 있다.

- **결과:** 렌더링 호스트를 별도로 둔다. CSP가 빠져도 동일 출처 정책(SOP) 격리가 남는다. 주소창만 보고도 관리 화면과 렌더링 화면을 구분할 수 있다.
- **트레이드오프:** 렌더링 호스트의 인증 문제가 새로 생기며, D-05로 해결한다.

## D-05. 렌더링 세션: 관리 앱 서명 토큰 핸드오프

| 대안 | 기각 이유 |
| --- | --- |
| 렌더링 호스트에 별도 로그인 화면 | 키를 두 번 입력해야 한다. 렌더링 호스트에 진짜 키 입력 화면이 있으면, 렌더링 문서가 띄운 가짜 화면과 구분할 수 없다 |
| 쿠키 공유 (`Domain=.example.com`) | 렌더링 호스트로 관리 세션 쿠키가 전송되어 분리한 의미가 사라진다 |
| DB에 1회용 코드 저장 | 동작은 하지만, GET 요청이 DB를 변경하게 되어 "GET은 상태를 바꾸지 않는다" 원칙과 충돌한다 |

- **결과:** 60초짜리 HMAC 서명 토큰을 쓴다. 서버에 상태를 남기지 않는다. 렌더링 호스트에는 로그인 화면이 없으며, 이 사실 자체를 "렌더링 화면은 키를 묻지 않는다"는 안전 안내로 활용한다.

## D-06. Fetch Metadata 검사로 하위 요청 차단

- **맥락:** 두 호스트는 같은 사이트라서, 렌더링 문서가 관리 호스트로 보내는 하위 요청에 관리 쿠키(Lax)가 실릴 수 있다. 응답은 CORS 때문에 읽을 수 없지만, 응답 시간 차이로 정보를 추측하는 공격(XS-Leak)은 가능하다.
- **결정:** 관리 호스트는 `Sec-Fetch-Site`가 `same-origin`/`none`인 요청과, 최상위 GET 이동만 허용한다.
- **장점:** 쿠키 전송 정책이 브라우저마다 달라도 영향을 받지 않는다. CSRF도 한 번 더 막는다.

## D-07. 업로드 HTML 내용을 필터링하지 않음

| 대안 | 기각 이유 |
| --- | --- |
| 정화(sanitize) | 실행 결과가 원본과 달라져 "그대로 실행해 본다"는 목적이 무너진다 |
| 위험 패턴 블랙리스트 | 우회 방법이 무수히 많아 보안 수단으로 믿을 수 없다 |

- **결과:** 보안은 실행 환경(렌더링 격리)에서 확보한다. 사용자 HTML이 `<meta>` CSP로 서버 정책을 완화할 수 없다는 점도 확인했다. meta CSP는 헤더 CSP에 추가로 적용될 뿐이고, meta 태그의 `sandbox` 지시어는 무시된다.

## D-08. 단일 렌더링 CSP, 외부 HTTPS 허용

| 대안 | 기각 이유 |
| --- | --- |
| STRICT/EXTENDED 프로필 2종 | 실질적인 보안 차이가 없다. STRICT도 `img-src https:`로 데이터를 외부로 보낼 수 있고, opaque origin 문서는 애초에 접근할 수 있는 비밀이 없다. 기획자는 둘 중 무엇을 골라야 할지 판단할 수 없다. 컬럼, 배지, 경고, 테스트가 프로필 수만큼 늘어난다 |
| CDN 허용 목록 (jsDelivr, cdnjs, unpkg) | unpkg와 jsDelivr는 누구나 올린 패키지를 그대로 제공하고, `'unsafe-inline'`도 이미 허용되어 있다. 따라서 보안 경계가 아니라 호환성 제약일 뿐이다. 오히려 AI 생성 HTML이 자주 쓰는 `cdn.tailwindcss.com`, `esm.sh`가 깨진다 |

- **결과:** 외부 HTTPS 스크립트, 스타일, 요청을 허용하는 단일 정책을 쓴다. 위험한 기능(`base`, `object`, 폼 전송, 팝업, `allow-same-origin`)만 막는다.

## D-09. HTML 최대 10MB, 단일 TEXT 컬럼

| 대안 | 기각 이유 |
| --- | --- |
| 1MB | 이미지를 base64로 넣은 단일 파일 HTML이나 번들러 산출물(`vite-plugin-singlefile`)은 수 MB가 흔하다 |
| 청크 분할 저장 | PostgreSQL TEXT는 1GB까지 담을 수 있고, TOAST가 자동으로 압축하고 분할한다. 애플리케이션에서 직접 나누면 조회, 수정, 트랜잭션만 복잡해진다 |
| 청크 분할 업로드 | 10MB는 multipart 요청 한 번이면 충분하다. 수십 MB 이상이나 이어받기가 필요해지면 에셋 스토리지와 함께 다시 검토한다 |

## D-10. multipart 전송

- **맥락:** `application/x-www-form-urlencoded`는 UTF-8 바이트를 `%XX`로 인코딩한다. 그래서 한글 위주 HTML은 요청 본문이 최대 3배로 커진다.
- **결과:** HTML을 보내는 폼은 모두 `multipart/form-data`로 전송한다. 요청 본문 제한은 11MB로 두고, HTML 크기는 디코딩한 뒤 10MB 이하인지 따로 검사한다.

## D-11. HTML 원본을 관리 화면에 싣지 않음

| 대안 | 기각 이유 |
| --- | --- |
| Monaco 초기값을 `<script type="application/json">` 블록에 인라인 | `</script` 이스케이프 규칙이 불완전하기 쉽다. 대문자 `</SCRIPT>`나 `<!--<script` 패턴이 블록을 벗어나면 사용자 HTML이 관리 화면 DOM에 주입된다. 주입된 HTMX 속성(`hx-post`, `hx-trigger="load"`)은 CSP `script-src 'self'`로도 막히지 않는다. 또 관리 화면은 압축하지 않기 때문에(D-14) 원본 크기만큼 페이지가 커진다 |
| 2MB 초과 시 앞부분 200KB만 표시 | 잘린 내용이 폼에 연결되어 원본을 덮어쓸 위험이 있다 |

- **결과:** 원본은 `text/plain` 응답(소스 보기, 다운로드)으로만 제공한다. 이후 에디터를 도입하더라도 `/source`에서 받아 오는 방식으로 넣는다.

## D-12. 등록·수정은 일반 폼, HTMX는 목록에만

- **맥락:**
  - HTMX는 기본 설정에서 4xx 응답을 화면에 반영하지 않는다. 그래서 검증 오류(422)가 나도 사용자에게는 아무 반응이 없는 것처럼 보인다.
  - `htmx:configRequest`는 폼 값을 수집한 뒤에 발생한다. 이 시점에 hidden 필드를 동기화하면 늦어서, 이전 내용이 전송된다.
- **결과:** 등록, 수정, 삭제는 일반 폼과 PRG(303)로 처리한다. HTMX는 목록 검색과 페이지네이션에만 쓰고, `allowEval:false`와 `selfRequestsOnly:true`로 설정한다.

## D-13. HTML 교체는 명시 플래그, 동시 수정은 version 비교

| 대안 | 기각 이유 |
| --- | --- |
| "HTML 필드가 비어 있으면 기존 값 유지" | 의도하지 않은 값이 필드에 들어가면(잘린 미리보기 등) 원본을 덮어쓴다 |
| 동시 수정 감지 없음 | 모든 EDITOR가 모든 문서를 수정할 수 있으므로, 나중에 저장한 사람이 앞사람의 수정을 모르게 덮어쓴다 |

- **결과:** `replace_html=1`일 때만 HTML을 저장한다. `version` 컬럼을 비교해 충돌이 나면 409를 반환한다. 수정자를 기록하는 `updated_by` 컬럼도 추가했다.

## D-14. 관리 화면 응답 압축 금지

- **맥락:** 관리 화면 응답에는 CSRF 토큰과 사용자 입력(검색어)이 함께 들어간다. 이 응답을 압축하면 응답 크기 변화를 관찰해 토큰을 알아내는 BREACH 공격의 조건이 성립한다.
- **결과:** 압축은 비밀이 없는 렌더링 응답과 정적 파일에만 적용한다. 원본을 관리 화면에 싣지 않으므로(D-11) 페이지가 작아서 압축으로 얻는 이득도 적다.
- **참고:** Hono `compress`는 gzip과 deflate만 지원한다. brotli가 필요하면 프록시에서 처리한다.

## D-15. 렌더링 캐시 `no-store`

| 대안 | 기각 이유 |
| --- | --- |
| ETag + 304 | 문서만 기준으로 ETag를 만들면, 재배포로 툴바 파일명이나 CSP 정책이 바뀌어도 304가 반환되어 옛 본문이 계속 쓰인다. 이를 막으려면 툴바 해시와 정책 해시를 ETag에 포함해야 하고, 압축 방식별로 약한 ETag도 써야 한다. 사용자가 적은 사내 도구에서 아끼는 대역폭에 비해 복잡도가 너무 크다 |

## D-16. 툴바: 표준 Web API, 문서 맨 끝 주입 (MVP 2)

| 대안 | 기각 이유 |
| --- | --- |
| Lit 또는 Custom Element | 사용자 페이지와 전역 `customElements` 레지스트리를 공유하므로, 같은 태그명이나 다른 버전의 Lit과 충돌할 수 있다. 버튼 몇 개짜리 UI에 비해 라이브러리 비용이 크다 |
| 마지막 `</body>` 앞에 주입 | 그 문자열이 사용자 인라인 스크립트 안에 있으면(`html += '</body>'`), 주입한 태그가 사용자 스크립트를 중간에 끊는다 |
| Shadow DOM만으로 스타일 격리 | host 요소 자체는 light DOM에 있어서 `body > *`, `div {}` 같은 사용자 CSS를 받는다 |

- **결과:** 툴바 스크립트는 문서 맨 끝에 덧붙인다. host 요소를 `document.documentElement`에 붙이고 `all: initial !important`를 지정한다. `?bare=1`이면 툴바를 끌 수 있다.

## D-17. `localStorage` 메모리 대체 (검증 조건부)

- **맥락:** opaque origin에서는 `localStorage`에 접근하면 예외가 발생한다. AI가 만든 프로토타입은 이 API를 자주 쓰기 때문에 그대로 두면 화면이 깨진다.
- **결정:** 메모리 기반 대체 구현을 `<head>` 시작 부분에 주입한다. 새로고침하면 데이터가 사라진다.
- **조건:** sandbox 문서에서 `window.localStorage`를 덮어쓸 수 있는지 브라우저별로 확인하지 못했다. 착수할 때 검증하고, 안 되는 브라우저가 있으면 이 기능을 빼고 안내 문구만 둔다.

## D-18. 링크 여러 개, JSONB 저장

| 대안 | 기각 이유 |
| --- | --- |
| 링크 1개 (`external_url`) | 기획서, Figma, 티켓 등 관련 자료가 보통 여러 개다 (사용자 요청) |
| 별도 `document_links` 테이블 | 링크는 항상 문서와 함께 읽고 쓰며 링크 단위로 검색하지 않는다. 테이블과 조인을 추가할 이유가 없다 |

## D-19. 검색 인덱스 없음

| 대안 | 기각 이유 |
| --- | --- |
| pg_trgm GIN 인덱스 | trigram 인덱스는 3글자 미만 검색에는 쓰이지 않는다. 그런데 "차트" 같은 2글자 한글 검색이 흔하다. 문서 수가 수백 건 수준이라 순차 스캔으로도 충분하다. drizzle-kit이 확장 생성을 지원하지 않아 수동 마이그레이션이 필요하다 |

## D-20. 계정 잠금 없음, IP 속도 제한만

| 대안 | 기각 이유 |
| --- | --- |
| 계정별 잠금 (5회 실패 시 15분) | 키는 추측이 불가능해서 잠금이 막아 줄 공격이 없다. 반대로 제3자가 일부러 특정 계정을 잠글 수 있다 |
| IP별 차단 (20회 실패 시 15분) | 사내 NAT 환경에서는 모든 사용자가 같은 IP로 보여서, 한 명의 실수로 전원이 잠긴다 |

- **결과:** IP별로 10분 안에 10회 실패하면 30초 동안 429를 응답한다. 프록시 설정(`TRUST_PROXY`)이 없으면 운영 환경에서 서버가 시작을 거부한다.

## D-21. Node.js 단일 런타임

- **대안:** Node.js와 Bun 중 하나를 고르지 않고 두는 안.
- **기각 이유:** 런타임마다 정적 파일 서빙, 해시 함수, 빌드 도구가 달라서 구현이 갈라진다.

## D-23. 브라우저 자동 테스트는 Chromium만

- **맥락:** Playwright의 WebKit은 실제 Safari와 다르다. 3종 브라우저를 자동화하려면 HTTPS 인증서, `__Host-` 쿠키, 테스트 엔드포인트 등 준비 비용이 크다.
- **결과:** Chromium만 CI에서 자동화한다. Safari와 Firefox는 릴리스 전에 수동 체크리스트로 확인한다.

## D-24. 문서를 독자별로 3개로 분리

## D-25. 호스트별 앱 분리 (모노레포)

| 대안 | 기각 이유 |
| --- | --- |
| 앱 하나가 `Host` 헤더로 관리·렌더링을 나눠 처리 | 두 호스트의 미들웨어가 한 프로세스에 있어서, 공통 미들웨어를 실수로 전역에 걸면 관리 CSP와 렌더링 CSP가 한 응답에 함께 붙는다. 렌더링 쪽이 관리 쪽과 같은 DB 권한을 가지게 된다 |
| 저장소 자체를 둘로 분리 | 세션·토큰·스키마를 두 저장소에서 맞춰야 한다. 핸드오프 토큰 형식처럼 양쪽이 반드시 같아야 하는 코드가 어긋날 위험이 크다 |

- **결과:** pnpm workspace 모노레포로 `apps/admin`, `apps/render`를 각각 독립 프로세스로 만든다. 공통 로직만 `packages/`(db, auth, shared)로 공유한다.
- **추가 이점:** render 앱은 `html_documents`를 읽기만 하는 DB 사용자로 접속한다. 렌더링 쪽에 결함이 생겨도 문서를 수정하거나 삭제할 수 없다.
- **트레이드오프:** 배포 단위가 둘이 된다. 스키마 변경이 있으면 마이그레이션 → admin → render 순서로 함께 배포한다.
