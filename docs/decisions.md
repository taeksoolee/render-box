## D-01. 사용자: 기획자가 올리고 개발자·디자이너가 본다

- **맥락:** 처음에는 개발자가 HTML을 테스트하는 도구로 설계했다. 실제 수요는 기획자가 AI로 만든 HTML을 개발자·디자이너에게 공유하는 흐름이었다.
- **뒤에 바뀐 점:** 실제로는 기획자·디자이너가 올리고 개발자가 보는 경우가 많다. 그래서 화면·문서에서 직군을 못 박지 않고 "올리는 사람(편집자) / 보는 사람(열람자)"으로 쓴다. 역할은 권한이고, 프로젝트마다 다르다 (D-37).
- **결과:**
  - 업로드는 코드 편집이 아니라 파일 드래그와 붙여넣기 중심으로 만든다.
  - 렌더링 프로필 같은 기술적 선택지를 없앤다.
  - AI 생성 HTML의 흔한 패턴(Tailwind CDN, `localStorage`, 상대 경로 이미지)에 대응한다.

## D-02. 인증: 개인별 접근 키

| 대안 | 기각 이유 |
| --- | --- |
| ID/비밀번호 | 사용자가 외워야 한다. 비밀번호 해시, 변경 화면, 계정 잠금 같은 부수 기능도 많아진다 |
| 팀 공용 키 하나 | 퇴사나 유출이 생기면 전원이 키를 바꿔야 하고, 누가 올렸는지 추적할 수 없다 |
| Google Workspace 로그인 | Google Cloud 쪽 OAuth 설정과 관리 부담이 생긴다 |
| 키를 URL에 포함 (`?key=`) | 브라우저 기록, 서버 로그, Referer로 키가 새어 나간다 |

- **결과:** 약 190bit 난수 키를 쓰고, DB에는 SHA-256 해시만 저장한다. 사람 단위로 회수할 수 있고, 역할 변경은 즉시 반영된다.
- **트레이드오프:** 운영자가 CLI로 키를 발급해 전달해야 한다. 사용자가 수십 명을 넘으면 다시 검토한다.

## D-03. 렌더링: 새 창, iframe 미사용

| 대안 | 기각 이유 |
| --- | --- |
| 관리 화면 안의 iframe | 관리 화면 기준으로 렌더링 호스트는 서드파티다. 서드파티 쿠키 차단 때문에 별도 토큰이 필요해진다. 렌더링 문서에서 무한 루프가 돌면 관리 화면까지 멈출 수 있다. iframe 크기와 sandbox 속성 때문에 실제 결과와도 달라진다 |

- **결과:** 렌더링은 항상 최상위 문서로 연다. 격리는 응답 헤더의 CSP `sandbox`로 적용한다. 그래서 링크를 직접 열어도 같은 격리가 적용된다.

## D-04. 관리·렌더링 호스트 분리

| 대안 | 기각 이유 |
| --- | --- |
| **단일 도메인** (`/r/*` 경로 + CSP sandbox) | 한때 채택했으나 독립 리뷰에서 뒤집었다 (아래 세 가지 이유) |

1. **격리 전제가 틀렸다.** 설계는 "opaque origin 문서가 보내는 하위 요청에는 `SameSite=Lax` 쿠키가 실리지 않는다"고 가정했다. 그런데 RFC 6265bis는 sandbox가 걸린 최상위 문서의 site-for-cookies를 **문서 URL의 출처**로 계산한다. 그래서 같은 호스트로 보내는 `<img>`나 `fetch(credentials:'include')`에는 쿠키가 실린다. 이 전제를 검증하던 테스트도 `fetch`의 기본 credentials 설정 때문에 항상 통과하도록 잘못 짜여 있었다.
2. **실패하면 전부 열린다(fail-open).** CSP 헤더가 한 번이라도 빠지면 사용자 JS가 관리 화면과 같은 출처가 되어 계정 전체가 탈취된다.
3. **신뢰하는 주소에서 피싱이 가능하다.** 렌더링 문서가 관리 화면과 같은 주소 아래에서 가짜 입력 화면을 띄울 수 있다.

- **결과:** 렌더링 호스트를 별도로 둔다. CSP가 빠져도 SOP 격리가 남고, 주소창만 봐도 두 화면을 구분할 수 있다.
- **트레이드오프:** 렌더링 호스트의 인증이 필요해졌다. 이 문제는 D-05로 해결한다.

## D-05. 렌더링 세션: 관리 앱 서명 토큰 핸드오프

| 대안 | 기각 이유 |
| --- | --- |
| 렌더링 호스트 자체 로그인 화면 | 키를 두 번 입력해야 한다. 또 렌더링 호스트에 진짜 키 입력 화면이 있으면, 렌더링 문서가 띄운 가짜 화면과 구분할 수 없다 |
| 쿠키 공유 (`Domain=`) | 관리 세션 쿠키가 렌더링 호스트로 전송되어 분리한 의미가 사라진다. `workers.dev`에서는 아예 불가능하다 |
| DB에 1회용 코드 저장 | GET 요청이 DB를 변경하게 된다 |

- **결과:** 60초짜리 HMAC 서명 토큰을 쓰고 서버에 상태를 남기지 않는다. 핸드오프의 모든 이동은 최상위 GET 내비게이션이므로, 두 호스트가 다른 사이트여도 동작한다.

## D-06. Fetch Metadata 검사로 하위 요청 차단

- **맥락:** 두 호스트가 같은 사이트일 때(로컬 `*.localhost`, 자체 도메인의 서브도메인) 렌더링 문서가 관리 호스트로 보내는 하위 요청에 관리 쿠키가 실릴 수 있다. 응답은 읽을 수 없지만, 응답 시간 차이로 정보를 추측하는 XS-Leak은 가능하다.
- **결정:** 관리 호스트는 `same-origin`/`none` 요청과 최상위 GET 이동만 허용한다.
- **장점:**
  - 호스트가 같은 사이트든 다른 사이트든 같은 코드로 막는다.
  - 브라우저마다 다른 쿠키 정책에 의존하지 않는다.
  - CSRF도 한 번 더 막는다.

## D-07. 업로드 HTML 내용을 필터링하지 않음

| 대안 | 기각 이유 |
| --- | --- |
| 정화(sanitize) | 실행 결과가 원본과 달라져 도구의 목적이 무너진다 |
| 위험 패턴 블랙리스트 | 우회 방법이 무수히 많아 보안 수단으로 믿을 수 없다 |

- **결과:** 보안은 실행 환경 격리로 확보한다. meta 태그로 넣은 CSP는 헤더 CSP를 완화할 수 없고, meta의 `sandbox` 지시어는 무시된다.

## D-08. 단일 렌더링 CSP, 외부 HTTPS 허용

| 대안 | 기각 이유 |
| --- | --- |
| STRICT/EXTENDED 프로필 2종 | 실질적인 보안 차이가 없다. STRICT도 `img-src https:`로 데이터를 내보낼 수 있다. 기획자는 둘 중 무엇을 골라야 할지 판단할 수 없다. 반면 컬럼, 배지, 테스트는 프로필 수만큼 늘어난다 |
| CDN 허용 목록 | unpkg나 jsDelivr는 누구나 올린 패키지를 그대로 제공하므로 보안 경계가 되지 못한다. 오히려 `cdn.tailwindcss.com`, `esm.sh` 같은 CDN을 쓰는 문서가 깨진다 |

## D-09. HTML 최대 10MB, PostgreSQL TEXT 단일 컬럼 — 대체됨

- PostgreSQL을 쓰던 때의 결정이다. 당시 청크 분할 저장은 "TOAST가 알아서 처리한다"는 이유로 기각했다.
- Cloudflare D1로 옮기면서 한 행에 약 2MB만 저장할 수 있게 되었고, 청크 저장이 다시 필요해졌다. → D-27

## D-10. multipart 전송 — 대체됨

- urlencoded로 보내면 한글이 최대 3배로 부풀어서 multipart를 택했었다.
- Workers 무료 플랜에서는 10MB multipart를 서버가 파싱하는 것 자체가 CPU 한도에 걸릴 수 있다. → D-29

## D-11. HTML 원본을 관리 화면에 싣지 않음

| 대안 | 기각 이유 |
| --- | --- |
| 에디터 초기값을 `<script type="application/json">`에 인라인 | 이스케이프 규칙이 불완전하기 쉽다. 사용자 HTML에 `</SCRIPT>`나 `<!--<script` 같은 패턴이 있으면 관리 화면 DOM에 그대로 주입된다. 주입된 HTMX 속성은 CSP로도 막히지 않는다 |
| 큰 문서는 앞부분만 표시 | 잘린 내용이 폼과 연결되어 있으면 원본을 덮어쓸 위험이 있다 |

- **결과:** 원본은 `text/plain` 응답(소스 보기, 다운로드)으로만 제공한다.

## D-12. 등록·수정은 일반 폼, HTMX는 목록에만

- **맥락:**
  - HTMX는 기본적으로 4xx 응답을 화면에 반영하지 않는다.
  - `htmx:configRequest` 이벤트는 폼 값을 수집한 뒤에 발생하므로, 그 시점에 hidden 필드를 동기화하면 이미 늦다.
- **결과:** 등록·수정·삭제는 일반 폼 + PRG(303)로 처리한다. HTMX는 목록 검색과 페이지네이션에만 쓴다.
- **D-39에서 바뀜:** 페이지 이동과 폼 전송에 `hx-boost`를 쓴다. 서버 처리는 그대로 일반 폼 + PRG다. 4xx 응답도 화면에 반영하도록 `responseHandling`을 설정했고, 업로드 폼(hidden 필드 동기화)은 boost하지 않는다.

## D-13. HTML 교체는 명시적 신호, 동시 수정은 version 비교

| 대안 | 기각 이유 |
| --- | --- |
| "HTML 필드가 비어 있으면 기존 값 유지" | 의도하지 않은 값이 필드에 들어가면 원본을 덮어쓴다 |
| 동시 수정 감지 없음 | 모든 EDITOR가 모든 문서를 수정할 수 있으므로, 누군가 앞사람의 수정을 모르고 덮어쓰게 된다 |

- **결과:**
  - HTML 교체는 `upload_id`가 있을 때만 일어난다 (D-29).
  - `version`을 비교해 충돌하면 409를 반환한다.
  - `updated_by` 컬럼을 추가한다.

## D-14. 관리 화면 응답 압축 금지

- **맥락:** 관리 화면 응답에는 CSRF 토큰과 사용자 입력(검색어)이 함께 담긴다. 이 응답을 압축하면 압축된 크기의 변화로 토큰을 알아내는 BREACH 공격이 가능해진다.
- **결과:**
  - 관리 화면 응답에 `Cache-Control: no-transform`을 붙여 Cloudflare 엣지가 압축하지 않게 한다.
  - 배포 후 실제로 압축되지 않는지 점검한다. 압축된다면 자체 도메인으로 옮길 때 Compression Rules로 끈다.
  - 렌더링 응답은 비밀 값이 없으므로 압축해도 된다.

## D-15. 렌더링 캐시 `no-store`

| 대안 | 기각 이유 |
| --- | --- |
| ETag + 304 | 재배포로 툴바 파일명이나 정책이 바뀌어도 304가 반환되어 옛 본문이 쓰인다. 이를 막으려면 ETag에 툴바·정책 해시를 넣어야 하는 등 복잡해진다. 소수 사용자 환경에서는 얻는 이득이 적다 |

## D-16. 툴바: 표준 Web API, 문서 맨 끝 주입 (MVP 2)

| 대안 | 기각 이유 |
| --- | --- |
| Lit 또는 Custom Element | 사용자 페이지와 전역 `customElements` 레지스트리를 공유하므로 같은 태그명이나 다른 버전의 Lit과 충돌할 수 있다 |
| 마지막 `</body>` 앞에 주입 | 그 문자열이 사용자 스크립트 안에 있으면 사용자 코드가 깨진다 |
| Shadow DOM만으로 스타일 격리 | host 요소 자체는 사용자 CSS의 영향을 받는다 |

- **결과:**
  - 툴바 스크립트는 문서 맨 끝에 덧붙인다.
  - host 요소를 `document.documentElement`에 붙이고 `all: initial !important`를 준다.
  - `?bare=1`이면 툴바를 끈다.

## D-17. `localStorage` 메모리 대체 (검증 조건부)

- **맥락:** opaque origin 문서에서는 `localStorage`에 접근하면 예외가 발생한다. AI 프로토타입은 이 API를 자주 쓴다.
- **결정:** 메모리 기반 대체 구현을 문서 앞부분에 주입한다. 새로고침하면 값이 사라진다.
- **조건:** sandbox 문서에서 `window.localStorage`를 덮어쓸 수 있는지 브라우저별로 확인한다. 안 되는 브라우저가 있으면 이 기능을 빼고 안내 문구만 남긴다.

## D-19. 검색 인덱스 없음

- **맥락:** 문서 수가 수백 건 수준이라 전체 스캔으로도 충분하다. 제목 부분 일치(`LIKE '%…%'`)는 일반 인덱스를 쓸 수 없다.
- **기각한 대안:** 전문 검색(PostgreSQL pg_trgm, SQLite FTS5). 이 규모에서는 비용 대비 이득이 없다. pg_trgm은 2글자 한글 검색에는 인덱스를 쓰지도 못한다.

## D-20. 계정 잠금 없음, IP 속도 제한만

| 대안 | 기각 이유 |
| --- | --- |
| 계정별 잠금 | 키는 추측이 불가능하므로 잠금이 막아 줄 공격이 없다. 반대로 제3자가 일부러 특정 계정을 잠글 수 있다 |
| IP별 장시간 차단 | 사무실 NAT 뒤에서는 전원이 같은 IP로 보이므로, 한 명의 실수로 전원이 잠긴다 |

- **결과:**
  - IP별로 10분에 10회 실패하면 30초간 429를 반환한다.
  - Worker에는 메모리 상태가 없으므로 실패 기록은 D1에 저장한다.
  - IP는 `CF-Connecting-IP`에서 읽는다.

## D-26. Cloudflare Workers 무료 플랜

| 대안 | 기각 이유 |
| --- | --- |
| Docker + Node 서버 (PostgreSQL) | 서버, DB 백업, 보안 패치를 직접 관리해야 한다. 소수 팀 도구에는 운영 부담이 크다 |
| Workers 유료 플랜 ($5/월) | 돈을 낼 거라면 가벼운 서버 한 대가 더 낫다 (사용자 판단) |
| 외부 서비스(CodePen 등) | "아무 데나 올리기"와 "우리 계정으로 통제되고, 로그인한 사람만 보고, 키를 회수할 수 있는 도구에 올리기"는 다르다 |

- **결과:** 무료 플랜 안에서 동작하는 것을 설계 제약으로 둔다.
  - 서버는 큰 데이터를 해석하지 않는다.
  - 인코딩 판별, 경고 같은 무거운 처리는 브라우저에서 한다.
  - Cron을 쓰지 않는다.
- **위험:** CPU 10ms 한도는 추정치다. 1단계에서 실측하고, 넘는 크기가 있으면 최대 크기를 낮춘다.
- **진행 순서:** 로컬(`wrangler dev`)에서 먼저 완성하고 검증한다. Cloudflare 계정 연결은 그다음에 한다.

## D-27. HTML 원본을 D1에 1MB 청크로 저장

| 대안 | 기각 이유 |
| --- | --- |
| R2 (객체 저장소) | 저장소로는 가장 적합하다. 다만 결제 수단을 등록해야 활성화할 수 있다 |
| KV | 값 하나에 25MB까지 들어가지만, 다른 지역에 반영되기까지 최대 60초가 걸린다. 교체 직후 옛 버전이 보일 수 있다. 무료 플랜은 저장 1GB, 하루 쓰기 1,000회로 제한이 크다 |
| 최대 2MB로 제한하고 D1 한 행에 저장 | base64 이미지를 넣은 HTML을 올릴 수 없다 |

- **결과:**
  - HTML 원본을 1MB씩 잘라 `html_chunks`에 저장한다.
  - 원본(`html_blobs`)과 문서(`html_documents`)를 분리해, 교체할 때 "새 원본 → 연결 변경 → 이전 원본 삭제" 순서로 처리한다.
  - 청크 분할은 처음에 사용자가 제안한 방식이다. PostgreSQL 때는 불필요했지만 D1에서는 이것이 정답이다.
- **조건:** D1은 값을 주고받을 때 직렬화를 거친다. 그래서 큰 문서에서 CPU 시간이 R2보다 많이 들 수 있다. 1단계 실측 결과로 최대 크기를 확정한다.
- **용량:** 무료 D1은 DB 하나당 500MB다. 부족해지면 R2로 옮긴다.

## D-28. 세션: 절대 만료, Cron 없이 지연 정리

| 대안 | 기각 이유 |
| --- | --- |
| 만료 없음 | 쿠키가 한 번 유출되면 키를 회수할 때까지 영구히 쓸 수 있다. 만료는 조회할 때 비교만 하면 되므로 비용이 들지 않는다 |
| Cron으로 만료 세션 정리 | 만료 판정에는 Cron이 필요 없고, 정리는 로그인할 때 함께 하면 된다 |
| 유휴 만료 + `last_seen_at` | 요청마다 DB 쓰기가 생긴다 |

- **결과:**
  - 발급 후 30일이 지나면 만료된다.
  - 만료 여부는 조회할 때 판정한다.
  - 정리는 로그인할 때 그 키의 만료된 세션을 지우는 방식으로 한다.

## D-29. 업로드 2단계: 원본 바이트 PUT + 메타데이터 폼

| 대안 | 기각 이유 |
| --- | --- |
| multipart 폼 하나로 전송 | 10MB multipart를 서버가 파싱하면 무료 플랜의 CPU 한도에 걸릴 수 있다 |
| 메타데이터를 헤더로 전송 | 한글 같은 비ASCII 문자와 여러 개의 링크를 헤더에 담기 어렵다 |

- **결과:**
  1. 브라우저 JS가 HTML 원본 바이트를 `PUT /uploads`로 보낸다.
  2. 서버는 파싱 없이 1MB씩 잘라 저장하고 `uploadId`를 돌려준다.
  3. 작은 일반 폼에 `upload_id`를 담아 제출한다.
- **연결되지 않은 업로드:** 저장되지 않고 남은 업로드는 같은 사용자의 다음 업로드 때 정리한다. Cron은 쓰지 않는다.
- **트레이드오프:** JS가 없으면 HTML을 올릴 수 없다. 인코딩 판별 등 업로드 보조 기능이 이미 JS에 의존하므로 수용한다.

## D-30. 도메인: `workers.dev`로 시작

| 대안 | 기각 이유 |
| --- | --- |
| 자체 도메인 | 도메인의 DNS가 Cloudflare에 있어야 한다. 지금 필요하지 않다 |
| 별도 도메인 구매 | 비용이 든다 |

- **결과:** `render-box-admin.<계정>.workers.dev`와 `render-box-render.<계정>.workers.dev`를 쓴다.
  - `workers.dev`는 Public Suffix List에 등록되어 있어, 두 호스트가 서로 다른 사이트로 취급된다. 격리 면에서는 오히려 더 강하다.
  - 대신 MVP 2 미리보기는 서명 토큰이 필요하다.
- **이전 방법:** 나중에 자체 도메인으로 옮길 때는 환경 변수만 바꾼다. 코드는 같은 사이트·다른 사이트 구성 모두에서 안전하게 동작하도록 작성한다 (D-06).

## D-31. 같은 폴더 이미지: 브라우저에서 HTML 안에 포함, 없으면 빈 상자

| 대안 | 기각 이유 |
| --- | --- |
| R2에 이미지 저장 후 서빙 | 결제 수단 등록이 필요하다. 문서 주소 구조(`/키/`)와 격리된 문서의 이미지 요청 인증도 다시 설계해야 한다 |
| 외부 이미지 호스팅 안내 | 내부 화면이 공개 주소로 나간다. 보관·삭제를 통제할 수 없다 |
| 경고만 하고 저장 허용 (기존) | 이미지가 깨진 문서가 그대로 공유된다 |
| 모든 이미지를 선택해야 저장 | 이 도구는 기획 공유용이고 디자인은 피그마로 공유한다. AI가 이름만 지어 넣은 경로처럼 파일이 원래 없는 경우 저장할 방법이 없어진다 |
| 서버에서 base64 변환 | 무료 플랜 CPU 한도(10ms)에 걸린다. 이미지가 서버를 거칠 이유가 없다 |

- **결과:** `<img src>`가 같은 폴더 파일을 가리키면 경로별로 이미지 파일을 받을 수 있게 한다. 저장할 때 브라우저가 선택한 파일은 `data:` URL로, 선택하지 않은 경로는 파일명이 적힌 빈 상자로 바꿔 HTML 한 파일로 올린다 (design.md 4.6).
- **유지되는 것:** 저장 구조(D1 청크), 렌더링, 보안 정책은 바뀌지 않는다.
- **트레이드오프:**
  - base64는 이미지 크기를 약 1.3배로 늘리므로, 10MB 한도 안에 넣을 수 있는 이미지는 약 7MB다.
  - CSS `url()`과 스크립트가 만드는 이미지는 대상이 아니다. 경고도 하지 않는다.
  - 변환은 브라우저에서만 한다. 서버 API를 직접 호출하면 경로가 그대로 저장되지만 이미지가 깨질 뿐 보안 문제는 아니다.

## D-32. AI 업로드 경로: 별도 Worker의 원격 MCP 서버, 개인 키 Bearer 인증

AI로 HTML을 만든 뒤 파일로 내려받아 다시 올리는 과정을 없앤다. "render-box에 올려 줘"로 끝나게 한다.

| 대안 | 기각 이유 |
| --- | --- |
| 관리 앱에 `/mcp` 경로 추가 | 쿠키·CSRF·화면 CSP를 쓰는 앱에 Bearer API가 섞인다. 앱 단위로 나누면 보안 경계와 배포가 분리된다 |
| 로컬 설치형(stdio) MCP | 사용자마다 설치·업데이트가 필요하다. 원격 서버는 주소와 키만 넣으면 된다 |
| 공식 SDK 사용 | 상태 없는 요청·응답 4가지 메서드만 필요하다. 직접 구현이 가볍고 Workers 런타임 호환 걱정이 없다. 호환성은 SDK 클라이언트 테스트로 확인한다 |
| OAuth 인증 | 이미 개인 접근 키가 있다. OAuth 서버를 따로 운영할 이유가 없다 |
| 삭제 도구 제공 | 되돌릴 수 없다. AI가 잘못 판단해도 문서가 사라지지 않게 웹 화면에서만 삭제한다 |

- **결과:** `apps/mcp`(D-33에서 `apps/api`로 이름 변경)가 `POST /mcp`로 `upload_html`, `update_html`, `list_html`, `get_html`을 제공한다. 문서 검증·저장 코드는 `packages/documents`로 옮겨 admin과 함께 쓴다 (design.md 11).
- **트레이드오프:**
  - AI가 HTML 전체를 도구 호출 인자로 다시 출력해야 하므로 토큰과 시간이 든다. 큰 문서는 웹 화면이 낫다. MCP 업로드 한도는 1MB다.
  - 키가 클라이언트 설정 파일에 평문으로 남는다.
  - 조직의 보안 프로그램(정보 유출 방지·네트워크 감시)이 MCP 통신도 똑같이 감시·차단할 수 있다. 보안 정책을 우회하는 수단이 아니며, 운영 전에 보안 담당자의 승인을 받는다.

## D-33. REST API: MCP와 같은 Worker(`apps/api`), HTML은 본문 그대로

스크립트·CI에서 curl 한 줄로 올리고 렌더링 URL을 받는다. MCP는 HTML을 JSON 안에 넣어야 해서 1MB로 제한했지만, REST는 파일을 본문 그대로 받으므로 웹과 같은 10MB까지 올릴 수 있다.

| 대안 | 기각 이유 |
| --- | --- |
| 관리 앱 `PUT /uploads`에 Bearer 인증 추가 | 쿠키·CSRF를 쓰는 앱에 다른 인증 방식이 섞인다 (D-32와 같은 이유) |
| REST용 Worker를 따로 둠 | 인증·문서 처리 코드가 MCP와 같다. 배포 대상만 늘어난다 |
| JSON 본문(`{"html": "..."}`) | 큰 JSON 파싱에 CPU 시간이 든다. 본문 그대로 받으면 디코딩 없이 청크로 저장된다 |
| multipart/form-data | 파싱하려면 본문 전체를 메모리에 올린다. 제목 등은 쿼리 파라미터로 충분하다 |
| 삭제 API 제공 | 스크립트 실수로 되돌릴 수 없는 삭제가 일어난다. 웹 화면에서만 삭제한다 |

- **결과:** `apps/mcp`를 `apps/api`로 바꾸고 `/api/v1`을 추가했다. 문서 처리는 `src/service.ts` 하나를 MCP 도구와 REST가 함께 쓴다 (design.md 11.4).
- **트레이드오프:**
  - 제목·설명·링크를 쿼리 파라미터로 받으므로 URL 인코딩이 필요하다 (curl은 `--url-query`).
  - D-32와 같이 조직의 보안 프로그램의 감시 대상이며, 정책을 우회하는 수단이 아니다.

## D-34. 브라우저 자동 테스트: Chromium·Firefox·WebKit, 순차 실행

D-23을 대체한다. Playwright 설정에 브라우저를 추가하는 것만으로 3종이 돌아갔고, 수정·충돌(409)·EUC-KR·붙여넣기·로그아웃·만료·모바일 흐름을 브라우저마다 반복해 확인하는 편이 수동 점검보다 싸다.

| 대안 | 기각 이유 |
| --- | --- |
| Chromium만 자동화 (D-23) | Firefox·Safari 차이(파일 읽기 오류, sandbox 동작 등)를 릴리스 직전 수동 점검에서야 발견한다 |
| 병렬 실행 | 로컬에서는 여러 Worker가 SQLite 파일 하나를 함께 써서 `Failed to get session commit token` 오류가 간헐적으로 난다 (운영 D1에는 해당 없음) |

- **결과:** `playwright.config.ts`에 chromium, firefox, webkit 프로젝트를 두고 worker 1개로 순차 실행한다. 서버만 검증하는 테스트(`e2e/api.spec.ts`, `e2e/mcp.spec.ts`)와 브라우저 고유 동작 테스트는 Chromium에서만 돈다.
- **트레이드오프:** Playwright WebKit은 실제 Safari가 아니다. 격리 항목(design.md 10.5)은 릴리스 전에 실제 Safari에서 한 번 더 확인한다.

## D-35. 버전 관리: 이전 원본 보존, 전체 용량 상한을 넘으면 업로드 거절, 삭제는 사람이

HTML을 교체하면 이전 원본이 바로 지워졌다. 실수로 다른 파일을 올리거나 AI가 `update_html`로 덮어쓰면 되돌릴 수 없었다. 이제 원본을 버전으로 남기고, 무료 D1 용량(500MB) 안에서 버티도록 전체 용량에 상한을 둔다.

| 대안 | 기각 이유 |
| --- | --- |
| 문서당 개수 제한 (예: 최근 10개) | 근거 없는 숫자다. 거의 안 바뀌는 문서는 칸이 남고, 자주 바뀌는 큰 문서 몇 개가 용량을 다 쓸 수 있다 |
| 상한을 넘으면 오래된 버전 자동 삭제 | 사람이 모르는 사이에 이력이 사라진다. 막히면 원인과 해결 방법(지우기)이 화면에 보이는 편이 낫다 |
| 상한 없음 | D1이 500MB에 닿으면 모든 쓰기가 실패해 로그인 세션도 못 만든다. 버전이 없어도 필요했다 |
| 복원할 때 원본 복사 | 10MB 복사는 용량과 CPU가 든다. 원본은 바뀌지 않으므로 같은 blob을 가리키면 된다 |
| 제목·설명·링크 변경도 버전으로 기록 | 렌더링 결과가 같은 버전이 쌓여 목록만 길어진다. 되돌릴 일이 드물고 다시 입력하기 쉽다 |
| 올린 사람만 버전 삭제 | 그 사람이 자리에 없으면 용량이 막힌 채로 남는다. 문서 삭제도 어느 EDITOR나 한다 |
| MCP·REST로 버전 삭제 | 되돌릴 수 없는 작업은 웹 화면에서 사람이 한다 (D-32, D-33) |

- **결과:** design.md 4.9, 6.6.
  - 렌더링 URL은 항상 최신본이다. 이전 본은 `/{key}/v/{seq}`로 본다.
  - 상한은 설정값(`STORAGE_LIMIT_MB`, 기본 400)이다. 오픈소스로 공개해 다른 계정·유료 플랜에서도 쓸 수 있게 하려는 것이다.
  - 경고 기준(기본 80%)을 넘으면 목록에 배너를 띄워, 막히기 전에 정리하게 한다.
- **트레이드오프:**
  - 용량이 차면 지울 때까지 팀 전체가 업로드를 못 한다. 경고 배너와 크기 순 정리 화면으로 줄인다.
  - 동시 업로드는 상한을 조금 넘을 수 있다 (D1 한도까지 100MB 여유).

## D-36. 오픈소스 공개: 운영 설정은 저장소 밖, `pnpm setup:remote`로 직접 배포

다른 팀이 자기 Cloudflare 계정에 배포해 쓸 수 있도록 MIT로 공개한다. 처음 운영 배포 때 D1 ID와 workers.dev 주소를 `wrangler.toml`에 직접 커밋했는데, 그대로 두면 받은 사람이 세 파일을 고쳐야 하고 원 저장소와 계속 충돌한다.

| 대안 | 기각 이유 |
| --- | --- |
| 실제 값을 `wrangler.toml`에 커밋 | 내 계정 값이 공개되고, 포크마다 세 파일을 고쳐야 한다. 업스트림을 받을 때마다 충돌한다 |
| wrangler 환경(`[env.production]`)에 값 넣기 | 여전히 저장소에 계정 값이 들어간다 |
| 배포할 때 `--var`로 값 넘기기 | D1 `database_id`는 명령줄로 넘길 수 없다 |
| 배포 안내 문서만 두고 손으로 설정 | D1 생성, 서브도메인 확인, 두 Worker에 같은 시크릿 등록을 빠뜨리기 쉽다. 이번 첫 배포에서도 순서를 맞추는 데 손이 많이 갔다 |
| 도움말 링크를 이 저장소로 고정 | 팀마다 자기 안내 페이지를 두고 싶을 수 있다. 원본 저장소 링크(하단)만 고정한다 |

- **결과:**
  - `render-box.deploy.json`(git 제외)에 계정 ID, D1 ID, 주소, 용량·도움말 설정을 둔다. 원격 명령은 여기서 만든 `wrangler.deploy.toml`(git 제외)로 실행한다 (design.md 9.3).
  - `pnpm setup:remote`가 로그인 확인, D1, 주소, 시크릿, 마이그레이션, 배포, 점검을 한 번에 하고, 다시 실행해도 안전하다.
  - README는 다른 공개 저장소와 같이 English summary 인용문 + 한국어 본문으로 쓴다. 사용 안내는 `docs/guide.md`이고, 관리 화면 상단 바·로그인 화면의 "도움말"이 이 문서로 연결된다 (`HELP_URL`).
  - 화면 하단에 원본 저장소 링크를 둔다. 렌더링 화면에는 아무것도 넣지 않는다 (격리, D-16).
  - CI(`.github/workflows/test.yml`)는 타입 검사와 단위 테스트만 돈다. 브라우저 테스트는 세 Worker를 띄워야 해서 로컬에서 돈다.
- **트레이드오프:** `render-box.deploy.json`을 잃어버리면 `pnpm setup:remote`를 다시 실행해 복구한다(이름으로 D1을 찾는다). 다만 `storageLimitMb` 같은 직접 바꾼 값은 다시 적어야 한다.
- **덧붙임 (환경):** 처음에는 Worker·D1 이름이 고정이라 같은 계정에 두 번째 배포를 만들면 첫 배포를 덮어썼다. `--env <이름>`이 이름 접두어와 설정 파일을 나누고, `teardown:remote`가 시험 환경을 지운다 (design.md 9.3). 다른 계정에 혼자 두는 환경은 접두어가 군더더기라 `--base-name`으로 이름을 정해 설정 파일에 남긴다. teardown은 지우기 전에 D1을 SQL로 내보내고, 실패하면 지우지 않는다(SQLite 파일보다 SQL이 `d1 execute`로 바로 되돌려 넣을 수 있어서).

## D-37. 프로젝트: 문서는 프로젝트 하나에, 역할은 프로젝트마다, 관리는 CLI로

여러 프로젝트(예: `tamna`)가 한 배포를 같이 쓰면, 지금은 키만 있으면 모든 문서가 보이고 편집자는 모든 문서를 고칠 수 있다. 프로젝트별로 볼 수 있는 사람과 고칠 수 있는 사람을 나눈다.

| 대안 | 기각 이유 |
| --- | --- |
| 이름을 팀(디자인팀 등)으로 | 문서는 프로젝트 단위로 모이고, 한 사람이 여러 프로젝트에 들어간다. 팀은 프로젝트 멤버십으로 표현된다 |
| 키마다 역할 하나 (지금처럼) | 한 사람이 A에서는 기획(편집자), B에서는 리뷰(열람자)인 경우를 표현할 수 없다 |
| 프로젝트별 용량 상한 | 한도는 D1 하나에서 나온다. 프로젝트마다 나누면 남는 곳과 모자라는 곳이 생긴다. 사용량만 프로젝트별로 보여 준다 |
| 모든 프로젝트를 보는 관리자 키 | 키 하나가 새면 전부 열린다. 운영자는 CLI(배포 권한)로 관리한다. → **D-38에서 채택으로 바꿈** |
| 웹 화면에서 프로젝트·멤버 관리 | 권한을 주는 화면은 공격 대상이 된다. 키 관리(D-02)와 같이 명령줄로 한다 |
| 렌더링 URL에 프로젝트 넣기 (`/tamna/{key}`) | 이미 공유한 주소가 깨진다. 문서 키가 이미 전체에서 고유하다. 문서를 옮겨도 주소가 그대로여야 한다 |
| 멤버가 아닌 문서는 403 | 문서가 있다는 사실이 드러난다. 404로 없는 문서와 같게 응답한다 |
| 프로젝트 삭제 명령 | 문서가 남은 프로젝트를 지우는 실수가 되돌릴 수 없다. 필요하면 문서를 옮기고 멤버를 뺀다. → **문서가 없는 프로젝트만 지우는 `project delete`로 바꿈** (쓰지 않는 `default`를 치우려고) |

- **결과:** design.md 3.9, 6.7. 렌더링·관리·API 세 곳 모두 문서의 프로젝트로 멤버십을 확인한다. 기존 데이터는 `default` 프로젝트로 옮긴다.
- **트레이드오프:**
  - 같은 D1을 쓰는 논리적 분리다. 완전한 분리가 필요하면 배포를 따로 한다 (D-36).
  - 요청마다 멤버십을 한 번 더 읽는다. 무료 플랜 읽기 한도에 비해 작다.

## D-38. 모든 프로젝트를 관리하는 관리자 키, 지정은 CLI로만

D-37에서는 전체 관리자 키를 두지 않았다. 운영해 보니 다른 사람이 만든 문서를 프로젝트에 상관없이 정리·관리하는 사람이 필요하다. 프로젝트가 늘 때마다 그 사람을 일일이 넣는 것은 빠뜨리기 쉽다.

| 대안 | 기각 이유 |
| --- | --- |
| 관리할 사람을 모든 프로젝트에 EDITOR로 넣기 (`grant --all`) | 새 프로젝트를 만들 때마다 다시 넣어야 하고, 빠뜨리면 그 프로젝트만 관리가 안 된다 |
| 관리자가 웹에서 키·멤버십까지 관리 | 권한을 주는 화면이 공격 대상이 된다. 키가 새면 새 키를 발급해 계속 들어올 수 있다. 키 관리는 CLI(배포 권한)로만 한다 (D-02, D-37) |
| 관리자 키는 API·MCP 금지, 웹만 | 관리자도 AI로 올리고 고칠 일이 있다. 대신 아래 장치로 줄인다 |
| 프로젝트마다 ADMIN 역할 (EDITOR는 내 문서만) | 지금 EDITOR가 이미 프로젝트 안의 모든 문서를 관리한다. 필요한 것은 프로젝트를 가로지르는 사람이다 |

- **결과:** `access_keys.is_admin`. 관리자 키는 멤버십과 상관없이 모든 프로젝트에서 EDITOR와 같다 (design.md 3.9). 지정·해제는 CLI로만 하고, 웹·API에는 키·프로젝트·멤버십을 바꾸는 기능이 없다.
- **트레이드오프:** 관리자 키가 새면 모든 프로젝트 문서가 열린다 (D-37이 기각한 이유 그대로). 그래서:
  - 관리자 키는 꼭 필요한 사람에게만, 적게 둔다. `pnpm key list`에 관리자 표시가 보인다.
  - 관리자 여부는 요청마다 읽으므로 `pnpm key admin <prefix> off`나 회수가 즉시 반영된다.
  - 키를 새로 발급하거나 남에게 권한을 줄 수는 없으므로, 유출돼도 회수하면 끝난다.

## D-39. 화면 속도: DB 가까이 실행, 쿼리 묶기, 해시 정적 파일, hx-boost, 근접 프리페치

페이지 이동이 느리고 깜빡였다. 운영에서 재 보니 한국에서 보낸 요청이 Cloudflare LAX에서 처리되고, D1은 APAC에 있다. 그래서 페이지 하나에 D1 왕복 4~6번이 태평양을 건넜다 (첫 응답까지 1.4~4초). 정적 파일 4개는 `max-age=0, must-revalidate`라 이동할 때마다 다시 확인했다.

| 대안 | 기각 이유 |
| --- | --- |
| 마우스를 올리면 프리페치만 | 응답이 수 초인데 마우스를 올리고 누르기까지는 0.2~0.4초다. 원인(왕복 수)을 먼저 줄여야 효과가 있다 |
| `<link rel=prefetch>` / Speculation Rules | 관리 화면은 `no-store`라 브라우저가 받아 둔 응답을 다시 쓰지 못한다. Speculation Rules는 Chromium만이고 인라인 스크립트가 CSP에 막힌다 |
| htmx preload 확장 | 브라우저 HTTP 캐시에 기대는데, `no-store`라 못 쓴다 |
| 관리 화면 캐시 허용(`private, max-age`) | 세션 토큰·문서가 든 페이지가 공용 PC 브라우저에 남는다. `no-store`는 유지한다 |
| htmx 기록 캐시(localStorage) | CSRF 토큰과 문서 내용이 localStorage에 남는다. 크기 0으로 끄고, 대신 app.js가 메모리에만 최근 페이지를 둔다 |
| 업로드 폼까지 boost | 폼 스크립트가 window에 끌어다 놓기 리스너를 단다. 본문만 바꾸면 리스너가 쌓인다 |
| 정적 파일 `max-age` 짧게 | 배포 직후 옛 CSS가 섞이고, 짧으면 다시 확인이 남는다. 내용 해시 이름이 둘 다 해결한다 |

- **결과:**
  - **Smart Placement**(`[placement] mode = "smart"`, 세 Worker): D1 가까이에서 실행한다. 한 요청의 D1 왕복이 가까운 곳에서 일어난다.
  - **인증 쿼리 묶기:** 세션·키 조회와 멤버십 조회를 D1 batch 한 번으로 한다 (`accessStatement`). 목록과 저장 공간 사용량은 동시에 조회한다.
  - **정적 파일:** `build:assets`가 내용 해시 이름으로 `/static/h/`에 복사하고 `manifest.json`을 쓴다 (`scripts/fingerprint-assets.ts`). `/static/h/*`는 1년 `immutable`. 로컬 개발은 원래 이름을 쓴다 (CSS 감시 모드).
  - **hx-boost:** 같은 출처 링크와 폼이 본문만 바꾼다. 로그인(렌더링 호스트를 거치는 다른 출처 이동)과 업로드 폼, 다운로드는 일반 이동이다. 오류 응답도 화면에 반영한다. 화면이 바뀌면 `#main`으로 포커스를 옮기고 live 영역에 알린다. 삭제 확인은 문서 수준 capture 리스너라 htmx 요청보다 먼저 막는다.
  - **근접 프리페치 (app.js):** 링크의 클릭 영역(목록 행은 행 전체)에서 64px 안에 마우스가 들어오면(10ms, 위치는 40ms마다 확인) 그 페이지를 받아 메모리에 20초 둔다. 키보드 포커스·터치·mousedown은 바로 받는다. 누르면 받아 둔 페이지로 본문을 바꾸고, 받는 중이면 기다린다. 쓸 수 없는 응답(오류, 로그인 이동)이면 htmx가 보통처럼 다시 요청한다. 동시에 둘까지, 프로젝트 전환 메뉴(누르면 선택을 기억한다)는 받지 않는다. 데이터를 바꾸는 요청 뒤에는 비운다.
  - **뒤로·앞으로 가기 (메모리 캐시):** boost로 떠나는 페이지를 메모리에 최근 10개(10분) 둔다. 뒤로·앞으로 가면 요청 없이 그대로 보여 준다(스크롤 포함). localStorage에는 두지 않으므로 새로 고치면 사라지고, 데이터를 바꾸는 요청(폼 전송 등) 뒤에는 비운다. 없으면 htmx가 본문만 서버에서 받는다(`refreshOnHistoryMiss: false`, `historyRestoreAsHxRequest: false`). 다시 붙인 화면도 버튼·폼이 동작하도록, 묶음 표시는 `data-*`가 아니라 WeakMap으로 한다.
  - **즉시 반응:** 페이지 요청이 80ms를 넘으면 화면 맨 위에 진행 막대를 띄우고, 누른 행은 새 페이지가 올 때까지 강조한다. 바로 바뀌는 경우(미리 받은 페이지, 메모리)에는 막대가 보이지 않는다.
- **트레이드오프:**
  - 뒤로 가기로 보는 페이지는 떠날 때 그대로다. 그 사이 다른 사람이 바꾼 내용은 새로 고쳐야 보인다 (브라우저 뒤로 가기 캐시와 같다).
  - 프리페치는 누르지 않은 페이지도 요청한다. 무료 플랜 요청 한도(하루 10만)와 D1 읽기 한도에 비하면 작지만, 목록을 오가면 요청이 늘어난다.
  - boost로 바뀐 페이지는 `<head>`를 다시 읽지 않는다. 배포 직후 이미 열린 화면은 새로 고칠 때까지 옛 CSS·JS를 쓴다.
  - Smart Placement는 트래픽을 보고 위치를 정하므로, 배포 직후 잠시는 효과가 없을 수 있다.

## D-40. iframe 직접 접근: 풀지 않고 올릴 때 경고만

화면을 `srcdoc` iframe에 넣고 부모가 `contentDocument`로 읽어 설명 번호를 올리는 프로토타입이 렌더링 화면에서 동작하지 않았다. 렌더링 문서와 그 iframe은 각자 출처가 없어(sandbox) 서로의 DOM에 접근할 수 없다.

| 대안 | 기각 이유 |
| --- | --- |
| 렌더링 CSP에 `allow-same-origin` | 문서가 렌더링 호스트의 진짜 출처를 갖는다. 모든 문서가 한 출처를 함께 쓰므로, 한 문서가 보는 사람의 세션으로 다른 문서를 불러와 읽고, 세션 쿠키·저장소를 건드릴 수 있다 (D-04, D-08) |
| 문서마다 서브도메인 + `allow-same-origin` | 안전하지만 와일드카드 자체 도메인, 렌더링 로그인 재설계, 기존 링크 이전이 필요하다. 이런 문서가 자주 나오면 다시 검토한다 |
| 그런 코드가 있으면 저장 거부 | 문자열 검사라 놓침(압축, `w["document"]`)과 오탐(try/catch, 주석)이 둘 다 있다. 오탐이면 올릴 방법이 없다. 내용은 거르지 않는다 (D-07) |
| 페이지 안에서 함수를 덮어써 막기 | 같은 페이지 코드가 iframe·프로토타입으로 원본을 되찾는다. 보안 장치가 아니다 |

- **결과:** 등록·수정 화면과 MCP 업로드가 같은 정규식으로 찾아 경고한다 (design.md 4.6). MCP는 결과의 `warnings`로 AI가 스스로 `postMessage` 방식으로 고쳐 다시 올리게 한다. 사용 안내·등록 화면의 "안 되는 것"에도 넣었다.
- **트레이드오프:** 경고를 무시하고 올리면 그 부분은 동작하지 않는다. REST 업로드는 검사하지 않는다.
